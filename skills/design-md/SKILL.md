# /design-md

프로젝트의 디자인 언어를 `DESIGN.md` 한 파일로 고정한다. AI가 시안 없는 화면을 만들 때
기본값으로 돌아가는 것을 막는 게 목적이다.

⚠ **이 스킬의 유일한 규칙: 관측한 것만 적는다.** 좋아 보이는 디자인 원칙을 창작해 넣지 마라 —
그 순간 이 파일은 "또 하나의 남의 스타일 가이드"가 되고, 사람이 다시 고치는 루프가 그대로 남는다.
모르는 항목은 지어내지 말고 `## Known Gaps`에 적는다.

## 0. 어느 길인가 — 먼저 가른다

| 상황 | 길 |
|---|---|
| 이 프로젝트에 화면·수정 이력이 있다 | **A. 관측** — 1~3장 |
| 새 도메인이라 이력이 없다 | **B. 벤치마킹** — B1~B3 |

⚠ **세 번째 길은 없다. 내가 디자인 언어를 지어내는 것.**
지어낸 규칙은 결국 쓰는 사람의 기본값이고, **그게 "AI 냄새"의 정체다.** 실측: 이 스킬로
랜딩 셋을 만들었는데 이력에서 캔 하나만 살아남았고, 지어낸 둘은 사용자가 "전체적으로 별론데
뭐가 별론지 모르겠다"고 했다. 규칙을 아무리 촘촘히 써도 **출처가 나면 결과도 나다.**

## A. 이력이 있을 때 — 관측

## 1. 근거 수집 — 이 순서대로

**(a) git 히스토리가 가장 강한 근거다.** 사람이 AI 결과물을 무엇으로 바꿨는지가 그대로 남아 있다.

```bash
git log --oneline --since="6 months ago" -i \
  --grep="디자인\|스타일\|톤\|통일\|정렬\|여백\|폰트\|간격\|design\|style" -- <앱경로>
```

같은 성격의 커밋이 여러 개면 그게 **반복 수정**이고, 곧 `Don't` 항목이다. diff에서
`className`/`class` 토큰을 뽑아 **추가된 것 vs 걷어낸 것**을 집계한다. 여러 커밋에 걸쳐
반복되는 토큰만 규칙으로 승격한다 — 한 커밋에만 있으면 그 화면 사정일 수 있다.

**(b) 현재 코드의 실사용 빈도.** 무엇이 실제로 쓰이는지가 무엇이 정의됐는지보다 중요하다.
토큰 정의 파일(`globals.css`·`tailwind.config`·`theme`)과 **실제 컴포넌트에서 쓰이는 클래스**를
따로 세서 비교한다. 정의됐지만 안 쓰이는 토큰은 디자인 언어가 아니다.

**(c) 기준이 되는 화면.** 대부분 랜딩·홈처럼 "가장 공들인 화면"이 기준이다. 어느 화면에 맞춰
나머지를 통일해 왔는지 커밋 메시지에서 찾고, 그 화면 코드를 직접 읽는다.

**(d) Figma MCP가 연결돼 있으면** `get_variable_defs`로 토큰을, `get_libraries`로 컴포넌트를
받아 (b)와 대조한다. 없으면 없는 대로 진행하고 `Known Gaps`에 적는다.

## B. 이력이 없을 때 — 실존 브랜드를 벤치마킹한다

근거는 [awesome-design-md](https://github.com/VoltAgent/awesome-design-md)의 브랜드별
`DESIGN.md`다 — 실존 브랜드를 분석한 73개이고, **진짜 디자이너가 만든 언어**다.

### B1. 브랜드를 고르기 **전에**, 도메인이 요구하는 것을 적는다

4~5줄이면 된다. 예(전세 보증금 위험 점검):

```
① 결론이 숫자다(137%)      → 큰 숫자를 크게 말하는 스케일이 있어야
② 문서를 화면에 얹어야 한다  → 표·문서 표면 규칙이 있어야
③ 위험 3단계 판정          → 시맨틱 팔레트(positive/warning/negative)가 있어야
④ 무서운 상황에서 읽는다     → 톤이 위협적이면 안 된다
```

이걸 먼저 안 적으면 **브랜드를 인상으로 고르게 된다.** "핀테크니까 Stripe"는 근거가 아니다.

### B2. 후보 2~3개의 파일을 **실제로 연다**

목록만 보고 고르지 마라. 브랜드 이름에 대한 내 인상은 그 브랜드의 디자인 언어가 아니다.

```bash
gh api repos/VoltAgent/awesome-design-md/contents/design-md/<brand>/DESIGN.md \
  --jq '.content' | base64 -d
```

500줄 안팎이라 **목차와 `Do's and Don'ts`만 봐도** B1의 요구사항과 맞는지 갈린다.

### B3. 근거를 대고 고른 뒤, 값을 그대로 쓴다

- **선택 근거를 결과물 머리에 적는다** — 나중에 사람이 "왜 이 브랜드인가"를 검증할 수 있게.
- 색·타입 스케일·반경·간격은 **그 파일의 값 그대로.** 예뻐 보이는 대로 손대면 B가 곧 A의 실패로 돌아간다.
- ⚠ **브랜드의 `Don't`가 내 판단과 충돌하면 브랜드를 따른다.** 실측: "브랜드색과 안전색을
  통일하자"고 정했던 것을 Wise의 Don't가 정면으로 금지했고(*never repurpose the brand green as
  a success indicator since it IS the CTA*), 브랜드 쪽이 옳았다.
- **값을 못 옮기는 것은 원칙을 옮긴다.** 독점 폰트·한글 미지원 폰트가 대표적이다. Wise Sans는
  독점이고 한글이 없다 → 파일이 지정한 대체안(Manrope 800/900)을 쓰되, **"디스플레이는 900"이라는
  원칙**을 한글 폰트에 이식한다. 값이 없다고 원칙까지 버리지 마라.
- 벤치마킹은 **최종 상태가 아니라 출발점이다.** 그 팀의 디자이너가 손대기 시작하면 그때부터
  A(관측)로 갈아탄다.

## 2. 쓴다

[DESIGN.md 규약](https://github.com/VoltAgent/awesome-design-md) 형식을 따른다:

```
## Overview          한 문단 — 이 제품이 어떤 인상이어야 하는가
## Colors            역할별. "무슨 색"만이 아니라 **위계를 무엇으로 만드는지**
## Typography        폰트 · 크기 스케일 · weight · letter-spacing · 숫자 처리
## Layout            여백 스케일 · 그리드 · 여백 철학
## Shapes            border-radius 스케일 · 테두리
## Components        버튼 · 카드/행 · 폼 · 배지 — 실제 쓰이는 아키타입
## Do's and Don'ts   ★ 이 파일에서 제일 중요한 절
## Responsive        브레이크포인트 · 터치 타깃 · 접힘 전략
## Known Gaps        확인 못 한 것
```

**`Do's and Don'ts`가 핵심이다.** 나머지는 코드를 읽으면 알 수 있지만, `Don't`는 사람의
수정 이력에만 있다. 각 항목은 **금지 대상과 대체재를 같이** 적는다:

```markdown
### Don't
- 시맨틱 텍스트 토큰(`text-text-sub`·`muted`·`dim`)으로 위계를 만들지 마라.
  → 위계는 `text-white/60` · `/50` · `/40` 투명도로 만든다.
- hover에 배경색을 쓰지 마라. → `hover:opacity-80`
```

- **추상적인 문장 금지.** "일관성 있게" · "적절한 여백" 같은 건 아무것도 강제하지 못한다.
  실제 클래스명·수치·토큰명으로 적는다.
- **근거 없는 항목 금지.** 각 규칙 옆에 어디서 관측했는지(커밋 해시·파일 경로)를 남기면
  나중에 사람이 검증할 수 있다.

## 3. 확인받는다

**초안을 보여주고 디자이너/사용자에게 확인받는다.** 이 파일은 앞으로 만들어질 모든 화면을
구속하므로 틀린 줄 하나가 오래 간다. 특히:

- 관측 근거가 약한 항목(커밋 1개에서만 나온 것)은 **표시해서** 물어본다.
- `Known Gaps`를 같이 보여준다 — 사람이 그 자리를 채워줄 수 있다.

## 4. 둘 곳

⚠ **`docs/{cycle}/DESIGN.md`(PDCA 설계 문서)와 이름이 같다. 절대 거기 쓰지 마라** — 사이클
폴더는 판단의 기록이고 아카이빙되면 묻힌다(폴더 규약상 7개 파일만 허용). 이 파일은 **앱 루트**다.

- 모노레포면 **앱마다** 둔다(`user/DESIGN.md`, `admin/DESIGN.md`) — 도메인마다 스타일이
  다른 게 정상이고, 하나로 합치면 둘 다 틀린다.
- 만든 뒤 그 앱의 `AGENTS.md`(또는 `CLAUDE.md`)에 **"UI 작업 전 `DESIGN.md`를 읽는다"** 한 줄을
  남긴다. 파일만 두면 안 읽힌다.

## 거의 항상 넣어야 하는 두 줄

관측이 아니라 **기본값**이다. 없어서 문제가 되는 걸 실사용에서 두 번 다 밟았다.

**1. 한글 줄바꿈** — 기본값이면 어절 중간에서 잘린다("규칙을 정하 / 고, 멈춘 것만").

```css
word-break: keep-all;      /* 공백에서만 끊는다 */
overflow-wrap: break-word; /* 끊을 데 없는 긴 토큰(URL·ID)만 강제로 */
```

**2. 컨테이너와 세로 리듬은 축을 갈라 쓴다** — `padding` 축약형끼리 부딪히면 **특이도 높은 쪽이
낮은 쪽을 통째로 지운다.** 실측: `.shell { padding: 0 18px }`(클래스)가
`section { padding: 60px 0 }`(엘리먼트)을 덮어써 **모든 섹션의 상하 여백이 사라졌다.**
눈에는 "간격이 좀 좁네"로만 보여서 발견이 늦다.

```css
.shell  { padding-inline: 18px; }  /* 가로만 */
section { padding-block: 60px; }   /* 세로만 — 논리 속성이라 애초에 안 부딪힌다 */
```

## 안 하는 것

- ❌ **A 경로(이력·디자이너가 있는 프로젝트)에서** 남의 브랜드 DESIGN.md를 가져오지 않는다.
  결과물이 그 브랜드처럼 되고, 여전히 이 팀이 원하는 게 아니라서 사람이 또 고친다.
  ⚠ 단 **B 경로(이력 없는 새 도메인)에서는 그게 정답이다** — 내가 지어내는 것보다 항상 낫다.
  이 문장을 B에까지 적용해서 창작으로 빠지는 것이 이 스킬의 가장 비싼 오독이다(실제로 그랬다).
- ❌ 디자인을 **개선**하지 않는다. 이 스킬은 지금의 디자인 언어를 **기록**한다. 개선 제안은
  따로, 사람이 요청할 때.
